## 1. 背景

第一轮已经把研究的核心闭环落进了引擎（2026-10-28）：

- **对比度守卫**：底栏常驻结果，详情弹层给出比值、建议色与「预览修复 → 取消 → 应用」，应用走事务、可撤销；
- **变更提案与幽灵草案**：候选文档在副本上整批试算后叠加渲染，不写入、不进历史；草案条提供「查看变更 / 对比旧版 / 放弃 / 采纳」；
- **变更卡**：固定展示「为什么改」与属性级 diff（与草案条共用一份状态）；
- **事务来源标注**：`manual / host / agent` + 不透明标签，写进历史节点。

因此本轮设计**不要重画**上述四块，只处理它们撑不起来的形态问题：

1. 变更卡现在是「草案条 + 底部浮层」，原型是右栏一级页签——页签形态从未设计过；
2. 意图输入区、作用域 chip、能力提示、起点牌全部未做（引擎只接受结构化提案，输入区归宿主）；
3. 评审态、场景切换、目标屏参数、演示锁未做（能力多归宿主，但界面形态要一次设计到位）。

交互优先：先定用户任务、状态与动作位置，再谈视觉。参考 DataV 的编排与预览、Figma 的评论/评审、v0 的接受/拒绝改动、Linear 的变更审阅；不要只换皮。

## 2. 本轮 OpenDesign 交付物

1. **低保真交互流**：每个用户任务的步骤、状态、动作与失败出口。
2. **高保真页面**：变更流页签、意图输入区、评审态、场景切换、目标屏与演示锁。
3. **可交互原型**：覆盖第 5 节状态矩阵；可点击、可切主题、可键盘操作。
4. **设计说明**：布局尺寸、与已实现部分的衔接决策、未采纳方案、仍需产品确认的问题。

原型是中间产物；最终实现必须落到仓库代码并验证，不以原型交付收尾。

## 3. 页面范围

### P1. 变更流页签（右栏一级）

- 右栏顶部现在有「检查器 / 变更」两个一级入口的语义，但实际只有检查器；本轮把「变更」做成真正的一级页签。
- 页签标题带待决计数；空态给「当前没有待处理变更」的明确出口，不做营销插画。
- 列表条目 = 一份提案：标题、作用域、影响组件数、来源（手动 / 宿主 / 平台）、状态（草案 / 待确认 / 已采纳 / 已拒绝）。
- 展开：为什么改（理由原文）、属性级 diff、受影响组件列表、画布定位。
- 底部动作：采纳、放弃；全部采纳需要二次确认，且在评审态隐藏。
- 与草案条的关系要明确：**草案条是画布上的常驻提示，页签是审阅场所**，两者状态必须同源，不允许出现「草案条已消失、页签里还有待决」。

### P2. 意图输入区（右栏底部常驻）

- 常驻在检查器下方，不浮动、不占满屏、不是独立页面。
- 结构：作用域 chip（来自画布选区）、单行输入、提交、能力提示；展开后可显示「本次能改 / 不能改」。
- 无选中时作用域为「整屏」，首次提交整屏修改需二次确认。
- 提交后进入「生成中」，**不流式输出正文**；结果只增加变更未读计数与草案条，不把右栏从检查器切走。
- 未接入时（宿主没有提供提案能力）输入区停用，说明原因，不模拟回复。
- 指代歧义：高亮候选让用户点选，不猜；作用域在输入中变化时提示「更新作用域」，不静默改写。

### P3. 评审态

- 只读：画布可查看不可编辑，输入区停用。
- 顶部显示发起人、审批人、进度；条目只保留批准 / 驳回。
- 逐条批准后该条转「已采纳（评审通过）」，全部处理完给明确收尾状态。
- 角色与人员数据来自平台；本设计不做账号、成员或权限管理界面。

### P4. 场景切换（左栏顶部）

- 场景是左栏一等公民：日常监控 / 应急指挥 / 汇报展示。
- 切换是整套布局与数据绑定的替换：先预览、后应用、可回退，并作为一条变更进入历史。
- 与「目标屏」不同：场景改变内容结构，目标屏只改变物理呈现参数。

### P5. 目标屏与演示锁

- 顶栏常驻目标屏入口：分辨率、拼接、点间距、观看距离、安全区、亮度。
- 画布叠加：安全区、拼接缝、3m 视角；三者可独立开关；3m 视角只做缩放与距离标注，不伪造景深。
- 演示锁：进入后只留画布与解锁提示；进入前要求没有待决草案；退出需二次确认（Esc 亦然）。

## 4. 用户任务与交互流

### T1. 从一句话到一份待审提案
选区 → 作用域 chip 出现 → 输入「把 KPI 带压成两行」→ 提交 → 生成中（可取消）→ 草案条出现、变更计数 +1 → 右栏仍在检查器。

### T2. 审阅并逐条采纳
点「查看变更」→ 右栏切到「变更」页签（或浮层，二选一，见第 6 节）→ 展开一条看理由与 diff → 定位到画布 → 采纳 → 草案条计数减一 → 全部采纳后草案条消失、修订号 +1。

### T3. 守卫失败与修复
底栏守卫变红 → 打开详情 → 失败项给出当前比值与建议色 → 预览修复（画布即时变化、文案标注未应用）→ 应用 → 该项转「待确认」→ 采纳 → 可撤销。

### T4. 评审
切换到评审态 → 输入区停用 → 逐条批准 / 驳回 → 进度更新 → 收尾。

### T5. 场景切换
左栏选场景 → 预览条（应用 / 取消）→ 应用 → 生成一条「场景切换」变更 → 可回退。

### T6. 目标屏与演示锁
打开目标屏参数 → 叠加安全区与拼接缝 → 进入演示锁（二次确认）→ Esc 退出（二次确认）。

## 5. 状态矩阵

| 维度 | 状态 | 界面表现 |
| --- | --- | --- |
| 能力 | 未接入 / 可用 / 只读 | 输入区停用并说明原因；只读时整个意图区隐藏 |
| 作用域 | 无选中 / 单组件 / 多选 / 整屏 | chip 文案与计数；整屏需二次确认 |
| 意图 | 空闲 / 输入中 / 生成中 / 失败 / 超时 | 失败保留输入与选区，不产生半成品 |
| 草案 | 无 / 存在 / 对比旧版 / 拒绝中 | 草案条、画布叠加、计数三处同源 |
| 守卫 | 通过 / 失败 / 修复预览 / 不可修复 | 修复预览为独立临时态，三处标注未应用 |
| 评审 | 普通 / 评审中 / 评审完成 | 评审中只读，隐藏全部采纳与输入区 |
| 场景 | 当前 / 预览中 / 切换失败 | 预览条提供应用与取消 |
| 演示锁 | 关闭 / 开启 | 只留画布与解锁提示 |
| 响应 | ≥1500 / 1320 / 1180 | 面板收窄、左栏收起、底栏折叠为计数 |

## 6. 与已实现部分的衔接（必须尊重）

1. **不要重画守卫条、草案条、变更卡**。它们已在引擎里，令牌与几何已定；本轮只决定「变更卡是否升级为页签」。
2. **守卫只有对比度一项**。不要设计成四项假数据；组件数、首屏、口径不在设计器内。
3. **草案只叠加受影响组件**，不是整屏半透明复制。视觉上要能看出「只有这几处在变」，其余画布保持清晰。
4. **检查器三页签（样式 / 数据 / 高级）不动**。变更页签是右栏的一级入口，不是第四个检查器页签。
5. **采纳 = 一次事务**。界面上不要出现「应用并发布」「修复即落稿」这类绕过采纳的动作。
6. **不出现「宿主」字样**；统一用「当前环境 / 平台 / 未接入」。

## 7. 布局与尺寸

- 顶栏 48px，底栏 30px；左侧导航轨 48px，左右面板 336px（≤1320 收窄到 300px，≤1180 收起左面板）。
- 列头 / 面板标题行 40px；控件 30px、紧凑 28px；图标 16px。
- 画布逻辑尺寸随目标屏变化；缩放与平移保留；面板折叠时布局不跳动。
- 变更页签宽度与检查器一致；条目不做营销式大卡片。

## 8. 设计令牌

沿用 Base Screen 既有令牌，不引入第二套设计语言：

- 浅色：workspace `#f4f4f4` / panel `#fcfcfc` / raised `#ffffff` / control `#f7f7f7` / canvas `#efefef`；
- 深色：`#1e1e1e` / `#0f0f0f` / `#080808` / `#161616` / `#282828`；
- 语义色：success 用于通过态、warning 用于「未写入 / 待确认」、danger 用于失败；语义色只做小面积提示，不做大面积底色；
- 选中态一律中性灰块 + 1px 收边；强调色只给主操作、焦点、当前定位与链接。

## 9. 交互与无障碍

- 键盘：`Ctrl K` 命令搜索、`Tab` 在面板内顺序移动、`Enter` 提交或采纳、`Esc` 按状态机逐级退出（关浮层 → 取消生成 / 放弃草案 → 取消场景预览 → 退出演示锁需二次确认）。
- 浮层使用 dialog 语义与焦点陷阱；草案、守卫、失败、采纳结果通过 `aria-live` 宣告。
- hover 不改变几何；卡片高度只在展开时变化；主题切换为根节点原子更新，不做逐属性补间。
- 断点变化时保持滚动位置与选中态。

## 10. 视觉禁区

- 浮动聊天球、全屏对话、独立 AI 页面；
- 机器人头像、聊天气泡、营销式大卡片；
- 用版本号标签命名变更集（用场合与动作，如「经营会 · 整屏编排」）；
- 把「AI 使用率」做成指标卡；
- 整片强调色的「采纳」按钮、彩色气泡；
- 给未接入能力伪造回复或示例数据。

## 11. 评审清单

1. 变更页签与草案条状态是否同源？会不会出现一处消失、一处仍有待决？
2. 右栏从检查器切到变更再切回，选中态与滚动位置是否保持？
3. 守卫失败 → 预览 → 应用 → 采纳 的四步，三处（卡片 / 画布 / 底栏）文案是否一致？
4. 输入区在未接入、只读、评审三种情况下是否都有明确出口且不伪造回复？
5. 场景预览与草案是否共用「未写入」语义，不会出现两条未写入的提示互相矛盾？
6. 演示锁进入前是否有待决草案阻断？退出是否二次确认？
7. 1300px 与 1180px 两个断点下，变更页签与草案条是否仍可操作？
8. 浅色 / 深色是否同构，语义色是否达到正文 4.5:1？
9. 键盘能否只靠 Tab / Enter / Esc 完成「提交 → 审阅 → 采纳」？
10. 是否误把组件数 / 首屏 / 口径做进了守卫？
