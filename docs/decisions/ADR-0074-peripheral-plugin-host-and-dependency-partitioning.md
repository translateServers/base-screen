# ADR-0074: 外围插件承载位置与依赖分区

> 状态：已接受
> 日期：2026-09-11
> 决策依据：设计评审（2026-09-11 通过）后，用户授权架构方按推荐方案决定后续决策，不再逐项评审
> 范围：核心库之外的能力承载位置、`packages/` 与外围插件的依赖分区、外围插件的信任与依赖准入；不包含执行隔离与沙箱
> 关联：[ADR-0084](./ADR-0084-plugin-contribution-vocabulary-and-trust.md)、[ADR-0019](./ADR-0019-designer-specialized-editor-dependencies.md)、[ADR-0027](./ADR-0027-lightweight-designer-foundation-host-processing.md)、[ADR-0029](./ADR-0029-host-managed-material-package-distribution.md)

## 背景

Base Screen 的能力要能在核心库之外实现与交付，否则两类内容无处安放：

1. **带第三方依赖的渲染类能力**（图表、地图、富文本、代码编辑器）。这类内容进不了核心库不是设计偏好，而是被机械约束拦住的：`scripts/check-boundaries.mjs` 的外部依赖白名单只有 `contracts: ['zod']`，任何其它包引入任何外部依赖都会以 `FORBIDDEN_EXTERNAL_DEPENDENCY` 失败。直接后果是 `packages/material/src/echarts/` 至今不是真 ECharts——它用 `createElementNS` 手绘折线、柱、圆点来近似图表，满足数据与事件契约但不提供真实图表能力。
2. **不想被核心库边界绑住的功能类能力**（命令、面板、检查器控件、数据资源类型、蓝图能力）。`packages/` 固定 12 个包、只发布 `dist`；把功能放进去意味着每个具体能力都要挤进固定的包清单、依赖白名单与基座发布节奏。

插件的承载协议本身已经就绪（6 类贡献、12 项能力、2 个端口、原子发布），缺的是**承载位置**与**依赖分区策略**。本决策补上这两个，使外围插件成为第三个信任档：宿主自写、**外围插件**、第三方（仍在范围外）。

## 决策

1. **新增顶层 `plugins/` 承载外围插件**，与 `packages/` 平行。`packages/` 保持固定 12 个包不变，`scripts/check-packages.mjs` 的约束范围不扩大到 `plugins/`。
2. **依赖白名单按区维护。** `packages/` 区维持现状（仅 `contracts` 可用 `zod`，React/Vue 仅作各自桥接包的 peer）。`plugins/` 区改为**逐插件显式申报**允许的外部依赖，不接受通配、不接受继承，由 `scripts/check-boundaries.mjs` 分区强制。
3. **依赖方向单向。** `plugins/*` 可以依赖 `packages/*` 的公共导出；`packages/*` **绝不**依赖 `plugins/*`，包含 dev 与 test 依赖。反向依赖一律失败关闭。
4. **外围插件不获得任何运行时特权。** 它必须走与宿主插件完全相同的通道：宿主显式提供候选、宿主加载、宿主授权。本决策不新增信任通道，也不改变 [ADR-0084](./ADR-0084-plugin-contribution-vocabulary-and-trust.md) 的同 realm 受信前提与 [ADR-0029](./ADR-0029-host-managed-material-package-distribution.md) 的"宿主负责加载与信任"边界。
5. **依赖准入沿用 [ADR-0019](./ADR-0019-designer-specialized-editor-dependencies.md) 的既有规则**：第三方依赖必须置于私有 adapter 之后；不导出第三方类型、状态或 document shape；adapter 以 canonical state 为唯一提交来源；安装前记录实际打包增量、lockfile 新增数、许可证、漏洞、维护状态、browser matrix 与移除方案。ADR-0019 保持有效——它约束的是"把依赖装进核心包"的路径，本决策走的是相反方向（把依赖留在核心库之外），因此是**扩展其准入规则到新位置，不取代它**。
6. **不引入版本标记字段与版本化命名。** [ADR-0084](./ADR-0084-plugin-contribution-vocabulary-and-trust.md) 与探索阶段约束继续生效。外围插件只依赖 `@base-screen/plugin-core` 与 `@base-screen/plugin-sdk` 的公共导出，契约偏差通过既有边界检查与规范快照发现，不通过版本协商发现。
7. **首批承载范围限于既有承载协议能表达的内容**：渲染类能力与现有 6 类贡献覆盖的功能类能力。本次不新增贡献类型、不新增能力，因此不启动描述符驱动的内核改造。
8. **`@base-screen/material` 现有手绘图表实现不因本决策自动移除。** 其去留（保留为无依赖降级实现，或整体移出核心库）属后续实施决策，不在本 ADR 范围内。
   > 后续处置（2026-09-11）：已决定**整体移出**。`base.echarts` 从 `packages/material` 删除，公共导出、`./echarts` 子路径、构建入口与自动注册一并移除；其受限 Editor Descriptor 载体以 `harness.semantic-chart` 迁入 `examples/browser-harness`（非发布物，沿用该工程既有的 `harness.*` 演示物料约定），继续承担 Descriptor 的浏览器端验证。核心库此后不再发布任何自称 ECharts 的物料，真实图表能力由外围插件 `plugins/plugin-echarts` 承载。

## 后果

- 核心库的外部依赖白名单与 12 包边界**保持不变**，但带第三方依赖的能力首次有了合规的承载位置。这是本决策的全部收益来源。
- `plugins/` 需要自己的构建、类型检查与边界约定，短期是纯新增的结构成本。
- 每个外围插件的依赖清单必须逐个显式申报。审核成本随插件数线性增长——这是刻意保留的：它把"要不要引入这个依赖"变成一次可见、可复核的决策，而不是一次静默的 `pnpm add`。
- 现有"任一插件激活失败即整体回滚"的语义在小规模插件集下仍然成立。插件数量增长后需要按插件分组原子发布（组内原子、组间独立），该决策留待实施阶段，且不得削弱"不留半成品目录"的既有性质。
  > 后续处置（2026-09-12）：该语义已在[外围插件分区 Spec](../specs/archive/peripheral-plugin-partition/spec.md) 实施中**提前改为每插件原子**——可归因到单插件的预检失败只排除该插件，运行期 `activate()` 失败只失效自身会话并级联其声明依赖方，不等待"插件数量增长"。未采用"按插件分组原子发布"的中间形态，因为每插件原子已同时满足收敛失败影响面与"不留半成品目录"；宿主自营物料解析失败仍为全局门。当前行为见[能力基线](../baseline/README.md)。
- **版本化设计仍未开放。** 若外围插件数量增长到无法靠同步升级维护，需要用户显式批准开启，届时另立 ADR 并明确是否退出探索阶段。本 ADR 不预支该批准。
- `plugin-sdk` 的作者面生产能力（`definePlugin` 家族在生产零使用）不在本决策范围内，但会立即成为瓶颈：外围插件数量一多，"每插件手写裸 runtime + 三处能力声明"的成本会乘 N。

## 被拒绝的替代方案

### 外围插件放宿主仓库

零结构调整，可沿用宿主已有的插件注入通道（XJDataHub 已经这样做）。拒绝原因：那样"基座侧承载面"就失去意义，基座团队无法独立编写、发布与验证外围插件，等于把本决策要解决的问题推给每个宿主各做一遍。

### 给核心库依赖白名单开口子

给 `packages/material` 增加受控外部依赖是最少改动的路径。拒绝原因：正是本决策要避免的结果——核心库一旦不再零第三方依赖，"核心库可被无负担嵌入"这一属性即失效，且无法回退。

### 本次直接引入版本化设计

可以让外围插件通过版本协商感知基座契约变化。拒绝原因：它与探索阶段的命名规则直接冲突，需要退出探索阶段的显式批准；而本决策选择"只依赖两个契约包的公共导出 + 规范快照校验"已能覆盖可预见的需求。在必要性出现之前不预支这一批准。

### 新增第 13 个核心包来承载

拒绝原因：包清单固定是刻意的边界手段；把承载位置放进 `packages/` 会让依赖白名单问题原样重现。

## 验证

实施后须满足以下条件；本 ADR 只授权方向，实施前仍需生效中的 Spec：

- `pnpm check:boundaries` 在 `plugins/` 分区下按各插件申报的依赖清单校验，并对未申报依赖失败关闭；`packages/` 区的行为与白名单逐字不变。
- 反向依赖检查生效：`packages/*` 对 `plugins/*` 的任何导入（含 dev、test）失败关闭。
- 一个带真实第三方依赖的外围插件能够合入，且 `packages/` 依赖白名单无任何变化。
- 该插件经"宿主提供候选 → 宿主授权 → 激活 → 目录原子发布"的完整路径可加载，且未新增任何信任通道或运行时特权。
- `pnpm check:docs` 与 `pnpm check:packages` 保持通过。
