## 一、问题缘起

在设计器里，一个组件（图表/表格/指标卡）需要绑定数据。当前 Base Screen 以"单个数据集资源"
为最小单元（`resourceType + resourceId`），配合 `params` 取值、`binding` 做字段投影。
现在的问题是：**一个组件要绑定复杂数据（多字段、参数联动、源字段与组件字段异构）时，
要不要引入一个叫"数据包"的概念？**

在回答之前，先看业界成熟做法（DataV）是怎么处理这件事的。

---

## 二、DataV 是怎么处理组件绑定复杂数据的

> 结论先行：**DataV 没有"数据包"这个一等实体。** 它把"组件绑定复杂数据"拆成一个
> **组件级的数据绑定配置**，而不是抽象出一个新的资源。

DataV 的数据模型是三层：

### 2.1 数据源（Data Source）——唯一"资源化"层

一个**命名、可复用**的数据定义（数据库 / API / 静态 JSON / CSV / 全局变量），在"数据准备"
集中管理。这是 DataV 里唯一被当作可复用资源的东西。组件并不直接内联数据库连接串或 URL，
而是通过 `dataSourceId` 引用。

### 2.2 组件数据配置（Data Source 页签）——组件级绑定对象

每个组件的右侧面板有一个"数据源"页签，它声明"我用哪个数据源"，并包含三件套：

| 配置项 | 作用 |
| ------ | ---- |
| **选择数据源** | 绑定到某个数据源（或静态 JSON / 全局变量） |
| **数据映射（Data Mapping）** | 把数据源字段映射到组件期望字段（如 `x/y/colorField`）。**异构数据→组件 schema 的适配全在这里** |
| **过滤器（Filter）** | 一段 JS 脚本，数据到达组件前做结构转换 / 筛选 / 计算 |

外加请求策略：禁止加载态、受控模式（不自动请求，仅由蓝图/事件触发）、自动更新（轮询）。

### 2.3 跨组件数据流——全局变量 + 蓝图

一个组件的数据要联动/被多个组件复用，DataV 不走"数据包"，而是走**全局变量**（命名、可赋值、
被组件引用）和**蓝图编辑器**（可视化编排数据流）。

### 2.4 对"数据包"的结论

DataV 只有两类可复用单元：

1. **数据源**（连接定义，可复用）
2. **全局变量**（数据值，可被多个组件引用）

它**没有**把"源 + 映射 + 过滤器"打包成一个命名的"数据包"让组件按名引用。复杂绑定是通过
**每个组件自己的绑定配置**（映射 + 过滤器）就地解决的。也就是说，DataV 的答案更接近
"组件级数据绑定契约"，而不是"可复用的数据包"。

## 三、Base Screen 现状（ADR-0023 契约）

当前 canonical 数据源（Contracts 持有）：

```ts
interface ScreenHostResourceDataSource {
  readonly type: 'host-resource';
  readonly resourceType: string;
  readonly resourceId: string;
  readonly params: Readonly<Record<string, ScreenHostResourceParameter>>;
  readonly binding: ScreenHostResourceBinding | null;
}

type ScreenHostResourceParameter =
  | { readonly kind: 'literal'; readonly value: ScreenJsonValue }
  | { readonly kind: 'variable'; readonly name: string };

interface ScreenHostResourceBinding {
  readonly fields: Readonly<Record<string, readonly string[]>>; // 角色 → 字段数组
}
```

配套的目录与解析能力：

- `ScreenHostDatasetCatalogPort.list/describe`：发现、描述数据集（字段 + 参数编辑器元数据）
- `ScreenHostResourcePort.resolve`：按 `resourceType + resourceId + params` 取数（每组件每实例）
- `ScreenDesignerHostAdapter.datasetCatalog + resources` 两个 capability
- 物料清单声明绑定角色（表格 `columns`；图表 `dimension` + 1..8 个 `measures`）

**ADR-0023 明确排除**：轮询、分页、运行时 sort/filter、跨组件缓存。

### 3.1 现状对照 DataV

| 能力 | DataV | Base Screen 现状 |
| ---- | ----- | ---------------- |
| 命名可复用数据源 | ✅ 数据源 | ✅ 数据集资源（catalog） |
| 字段映射（源→组件字段） | ✅ 数据映射 | ✅ `binding.fields`（角色→字段） |
| 组件级绑定数据源 | ✅ 组件数据源页签 | ✅ 每个组件数据源自带 params+binding |
| 过滤器（JS 转换） | ✅ 过滤器 | ❌ 明确 out of scope |
| 跨组件数据复用 | ✅ 全局变量 + 蓝图 | ⚠️ `variables` 已有，蓝图见 ADR-0026 |
| 命名的"数据包"（源+映射+过滤器打包） | ❌ 无 | ❌ 无 |

结论：**在"单组件绑定复杂数据"这件事上，Base Screen 已经基本对齐 DataV**——缺的主要是
"过滤器/转换"这一层，而不是缺一个"数据包"。

## 四、核心判断："数据包"要不要有？

基于上面的事实，我的判断是：

> **"数据包"只有在"需要一个命名、可复用、可被多个组件共享的组合单元"时才有意义。**

要分两种情况讨论：

### 情形 A：只解决"单组件绑定复杂数据"

那 DataV 的答案已经够了——**组件级数据绑定契约**（选源 + 映射 + 过滤器），**不需要**新增
"数据包"实体。当前缺的只是过滤器/转换层。这符合 ADR-0023 "host-neutral 精简数据流" 的方向，
改动最小、最贴领域模型（`Screen*` 前缀）。

### 情形 B：要"命名、可复用、多组件共享的数据单元"

那"数据包"才成立——它本质上是 DataV 里"数据源 + 预置映射 + 预置过滤器/参数"的**合成物**，
打成一个命名资源，多个组件按名引用、共享同一份绑定意图。这带来额外价值（复用、一致性、
一处修改多处生效），但也带来额外成本（新一等实体、共享/引用语义、生命周期、快照/发布影响）。

### 两种情形的取舍

| 维度 | A：组件级绑定契约 | B：可复用的数据包资源 |
| ---- | ---------------- | ------------------- |
| 一等实体 | 否（沿用现状资源） | 是（新增） |
| 多组件共享 | 不强（各自绑定） | 强（按名引用） |
| 一处修改多处生效 | 否 | 是 |
| 改动范围 | 小（补转换层） | 大（新契约 + 引用语义 + 快照/发布） |
| 贴 DataV | 高 | 低（DataV 并无此物） |
| 风险 | 低 | 中（语义/生命周期复杂度） |

---

## 五、建议与待拍板项

**建议**：默认走**情形 A**——先补"过滤器/转换层"，不引入"数据包"一等实体。理由：

1. 我们已经在"单组件绑定复杂数据"上对齐 DataV，剩余缺口只是转换层。
2. 引入共享"数据包"会增加引用语义、生命周期、快照/发布一致性的复杂度，而在 DataV 这类
   成熟产品里，跨组件共享是用"全局变量 + 蓝图"而非"数据包"解决的——这条路我们已有
   `variables` 和蓝图（ADR-0026）雏形。
3. 符合 ADR-0023 的 host-neutral、精简数据流方向，避免把宿主/共享状态设计泄露进 Screen Document。

**待团队拍板的点**：

1. 是否只需要"单组件复杂绑定"（→ 情形 A，补转换层即可）？
2. 是否真有"同一份绑定意图要被多个组件共享、且一处改处处生效"的强诉求？
3. 若 B 成立，是否接受为此新增一等实体，并承担快照/发布/引用语义的成本？
